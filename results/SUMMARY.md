# Итоги этапа 1 — 2026-10-04

Синтетика по шаблону записи OpenResearch/OpenScience (см. `../README.md`).
Точка = 30 с, первые 5 с отброшены; сообщение 1 КБ → +200–500 Б за сброс,
потолок 64 КБ, новое сообщение (INSERT) каждые 160 сбросов. Docker Desktop
на macOS, VM linuxkit, 8 ядер, Python 3, SQLite 3.40.1. Один прогон на точку.

## Выводы (только то, что видно в данных)

1. **Bind-mount с macOS: общий файл SQLite в WAL портится при ≥5 процессах.**
   В `one-file` на bind-mount 58–98 % записей вернули
   `database disk image is malformed` при N = 5…100; при N = 1 — ни одной.
   После прогона `PRAGMA integrity_check` не прошла база в точках N = 5, 10,
   20, 50 и в первой попытке N = 100 (повтор N = 100 прошёл проверку, но
   75 % записей всё равно вернули malformed). Те же базы по одной на процесс
   (`file-per-session`) и JSON-файлы — ноль ошибок и ноль битых. Копии
   испорченных баз — вне репозитория, `~/bench-state/corrupt/`.
   Это и есть урок OpenHuman «хранилище ломает среда», воспроизведённый
   на синтетике. Причину не установил: простые проверки POSIX-блокировок
   `fcntl`, общего `mmap` и `pwrite`/`pread` между двумя процессами на этой
   ФС прошли — механизм порчи остаётся открытым вопросом.
2. **Откат на `journal_mode=TRUNCATE` на той же ФС убирает порчу, но
   не держит темп.** `one-file` + TRUNCATE на bind-mount: ноль malformed,
   но p99 = 68 мс уже при N = 5, 244 мс при N = 10, 955 мс при N = 20; при
   N = 50 выполняется 25 % целевых сбросов и появляются 7 ошибок
   `database is locked`. Это ровно цена отката OpenHuman (PR #2455).
3. **ФС контейнера: `one-file` держит 75 мс до N ≈ 20, граница — между 20 и
   100, ломается к 150–200.** Два прогона дали разное: p99 при N = 50 —
   46 и 261 мс, при N = 100 — 60 и 161 мс; при N = 20 — 14 и 71 мс. Доля
   записей дольше 75 мс: ≤1 % до N = 20, 0,7–2,5 % при N = 50–100,
   10 % при N = 150, 14 % при N = 200. При N = 200 выполнено только 36 %
   целевых сбросов, p99 = 2,7 с, худшая запись 11 с. Разброс между
   прогонами сопоставим с самим эффектом — точный порог одним прогоном
   не определить.
4. **`database is locked` на ФС контейнера не появилась ни разу** (до N = 200
   включительно): `busy_timeout = 5000` поглощает конкуренцию — ценой
   задержки, а не ошибки. Механизм в коде OpenResearch (WAL + busy_timeout)
   ведёт себя так, как задуман, — пока он на «правильной» ФС.
5. **Дробление хранилища снимает конкуренцию на ФС контейнера.**
   `file-per-session` при N = 100: p99 8–36 мс против 60–161 мс у
   `one-file`; при N = 200: p99 84 мс и 92 % сбросов против 2,7 с и 36 %.
   JSON + rename: p99 ≤ 12,5 мс во всех точках до N = 100 при любом интервале.
6. **На bind-mount упирается сама ФС, а не общий файл.** `file-per-session`
   на bind-mount при N = 50 и 100: p99 598 и 446 мс, выполнено 67 % и 47 %
   сбросов, при этом в 12 и 24 окнах половина агентов стоит одновременно —
   общий стопор ФС, а не очередь на один файл. JSON на 75 мс при N = 100:
   p99 324 мс, 81 % сбросов. JSON на 250 мс выдерживает N = 100
   (p99 22 мс) — у OpenScience частота втрое ниже, и на этой ФС это решает.
7. **Задержки ожидания в SQLite квантуются.** Медленные записи `one-file`
   кучкуются около 88, 113, 140, 197, 250 мс — это шаги встроенного
   busy-handler SQLite (сон 1, 2, 5, 10, 15, 20, 25, 25, 25, 50, 50, 100 мс).
   Писатель, попавший на занятый замок, ждёт до следующего шага, даже если
   замок освободился раньше. Пачки по многим агентам одновременно (например,
   t = 7,3 / 16,3 / 21,4 с при N = 50) похожи на WAL-checkpoint, но это
   гипотеза, отдельно не проверял.

## Проверка на сон мака / паузу VM

Координатор заметил, что часы контейнера отстали на ~11,5 мин (вероятно,
мак засыпал). Поэтому: все длительности меряются `time.monotonic()`; для
каждой точки записываются `gap_max_ms` (макс. интервал между сбросами любого
агента) и `clock_drift_s` (расхождение настенных и монотонных часов); точка
с `gap_max_ms > 5000` или `|clock_drift_s| > 1` перезапускается один раз.

- Первый прогон матрицы (до перехода на monotonic) выброшен целиком.
- Расхождение часов > 1 с не встретилось ни в одной точке (макс. 0,11 с).
- `gap_max_ms > 5000` сработал в четырёх точках, все — `one-file` под
  тяжёлой нагрузкой: bind N = 5 (обе попытки, 10,8 с в итоговой), bind
  N = 100 (первая попытка; повтор чистый, 1,0 с), bind+TRUNCATE N = 50
  (обе, 5,1 с), контейнер N = 200 (обе, 8,9 с). Ни в одной часы не
  разошлись, а остальные режимы на тех же N и в те же минуты разрывов не
  показали — поэтому считаю это поведением SQLite под конкуренцией/порчей,
  а не паузой VM. В `summary.json` такие точки помечены
  `suspect_pause = true`, `attempt = 2`.
- Синхронные стопоры (`sync_stalls`) почти отсутствуют на ФС контейнера
  и массово есть на bind-mount (`file-per-session` N = 50/100) — это
  отнесено к ФС, см. вывод 6.

## Чего данные не показывают

- N > 8 — процессов больше, чем ядер: часть задержки при N ≥ 50 даёт
  планировщик. Контроль — `file-per-session` на том же N.
- Один прогон на точку; разброс между прогонами на ФС контейнера большой
  (вывод 3). Для слайда нужны ≥3 повтора на пограничных N (20–100).
- Механизм порчи на bind-mount не установлен (вывод 1).

# Этап 2 — журнал событий (2026-10-04)

Агенты с тем же шаблоном (75 мс, рост 1→64 КБ, новое сообщение каждые 160
сбросов) не пишут в файл: каждый сброс — событие с полным текстом в брокер.
Один процесс-компактор читает журнал пачками, оставляет последнюю версию
строки и пишет в SQLite (WAL, `synchronous=NORMAL`) одной транзакцией на
пачку. Брокеры: **Redis Streams** 8.10.2 (`XADD` / `XREAD BLOCK` /
`XTRIM MINID` после коммита) и **Kafka** 4.3.1 (KRaft, один узел, одна
партиция, продюсер librdkafka 2.15.1 с `acks=1` и ожиданием подтверждения).
Оба на 127.0.0.1, данные брокеров — на ФС контейнера; ФС меняется только для
базы компактора. Агенты и компактор — Python 3.12 (SQLite 3.53.4). Точка —
30 с, первые 5 отброшены; один прогон на точку. Код — `../eventlog.py`,
`../brokers.sh`, как запускать — `../README.md`, «Этап 2».

«Публикация» — время агента от начала `XADD`/`produce` до ответа брокера
(аналог `write_*` этапа 1: то, что тормозит агента). «e2e» — от начала
публикации до `COMMIT` компактора (свежесть состояния), по общему для
процессов `CLOCK_MONOTONIC`.

## Выводы (только то, что видно в данных)

1. **Агента журнал не тормозит ни на одной ФС.** p99 публикации у Redis —
   ≤ 15,3 мс до N = 200 на ФС контейнера и ≤ 19 мс до N = 100 на папке мака;
   у Kafka — ≤ 14 мс до N = 100 на обеих, 60–76 мс при N = 150–200 (доля
   публикаций дольше 75 мс ≤ 1 %). Выполнено ≥ 98 % целевых сбросов во всех
   точках, кроме Kafka N = 1 и 5 на контейнере (90 и 96 %, см. оговорки).
   Для сравнения при N = 200 на контейнере общий файл — p99 2,7 с и 36 %
   сбросов, файл на сессию — 84 мс.
2. **На папке мака журнал убирает порчу из картины.** Ноль ошибок
   публикации и компактора, `integrity_check` базы компактора прошёл,
   итоговое состояние совпало с последним опубликованным текстом
   (`state_mismatch = 0`) во всех 28 точках — там, где общий файл в WAL
   давал 58–98 % записей «malformed», а файл на сессию при N = 50–100 —
   p99 446–598 мс и 47–67 % сбросов.
3. **Цена переезжает в свежесть состояния, и её задаёт ФС базы.** На ФС
   контейнера e2e p99 = 11–27 мс до N = 50 у обоих брокеров (у Redis — до
   N = 150, 25 мс). На папке мака e2e p99 растёт с N: 25–58 мс при N ≤ 20,
   167–202 мс при N = 50, 349–521 мс при N = 100; доля событий, дошедших до
   базы позже 75 мс, при N = 100 — 54–58 %. Компактор при N = 100 на папке
   мака проводит в коммитах 79 % времени (p99 коммита 99–135 мс) — это
   ближайший потолок схемы на этой ФС.
4. **Компактор успевает во всех точках.** Ни одного события с e2e > 1 с
   (максимум 710 мс — Kafka, N = 150, контейнер); очередь в журнале — не
   больше 786 событий (≈ 0,3 с трафика при N = 200, 2,65 тыс. событий/с,
   ~76 МБ/с полного текста); после остановки агентов компактор дописывает
   ≤ 384 мс. Неограниченного роста лага нет.
5. **Схлопывание почти не участвует.** На ФС контейнера компактор забирает
   1–4 события за пачку (18 у Redis при N = 200), событий на записанную
   строку ≤ 1,04; на папке мака при N = 100 — 1,3–1,4. Выигрыш даёт сам
   единственный писатель (коммит p99 ≤ 27 мс на контейнере при любом N),
   а не пакетирование.
6. **Redis и Kafka одинаковы до N = 50, дальше Kafka хуже.** При N = 100–200
   на контейнере у Kafka e2e p99 118–510 мс против 24–124 мс у Redis и
   p99 публикации 60–76 мс против 3–15 мс при N = 150–200. Причину не
   устанавливал: JVM-брокер делит 8 ядер с 150–200 процессами агентов,
   продюсер ждёт подтверждения каждого сообщения (`flush` на событие).
   Гарантии у них разные (см. оговорки), это не сравнение «кто быстрее
   вообще».

Немонотонность, которую не объясняю: на папке мака e2e **p50** при N = 50
(2–4 мс) ниже, чем при N = 20 (14–20 мс), у обоих брокеров; p99 при этом
растёт монотонно.

## Оговорки этапа 2

- **Брокер на той же машине.** Сети нет; брокер и компактор делят 8 ядер с
  агентами. На отдельном узле публикация получит сетевой RTT, а агенты
  перестанут делить CPU с брокером.
- **Компактор один и на Python.** Его потолок (вывод 3) — потолок этой
  реализации; отказ и перезапуск компактора, повторное чтение журнала не
  проверялись.
- **Гарантии сохранности разные и слабее «записал в SQLite».** Redis
  запущен без персистентности (журнал в памяти до подрезки); Kafka пишет в
  page cache без `fsync` на сообщение (по умолчанию); `acks=1` на одном
  узле. Падение брокера не моделировалось.
- **Событие = полный текст**, как сброс в этапе 1. Вариант с дельтой
  (меньше трафика, но компактор должен склеивать) не мерился.
- **Не измерено:** чтение состояния интерфейсом во время записи (аналог
  `orx serve`), читатели самого журнала, несколько партиций/компакторов.
- **Один прогон на точку.** Kafka N = 1 и 5 на контейнере в основной матрице
  выполнили 90 и 96 % сбросов: агенты стояли вне публикации (разрывы между

  записи < 20 мс). Повтор этих двух точек
  (`2026-10-04-container-eventlog-kafka-recheck/`) дал 100,2 % сбросов,

- **Часы.** Пауз VM не было: `gap_max_ms` ≤ 797 мс, `clock_drift_s` ≤ 0,01 с

# H3: окно пачки компактора (2026-10-04)

**Гипотеза.** Потолок компактора — коммит на каждую маленькую пачку. Если
компактор копит события окном W мс перед коммитом и схлопывает события одной
строки до последнего текста, ёмкость вырастет, а свежесть ухудшится
предсказуемо.

**Как мерили.** `eventlog.py --batch-window-ms W`: получив первое событие
пачки, компактор ещё W мс добирает журнал (`XREAD BLOCK` на остаток окна) и
только потом коммитит; на строку (session, turn) в пачке пишется последний
текст. W = 0 — прежнее поведение (одно чтение журнала, до 500 событий, и
коммит). Только Redis Streams, W ∈ {0, 25, 75} мс, N ∈ {20, 50, 100, 200},
база компактора на ФС контейнера и на папке мака; точка 30 с, 5 с прогрева,
один прогон на точку. Запуск:
`run_matrix.py --configs event-log-redis --batch-window-ms 0,25,75`.

«Ёмкость» — событий, закоммиченных за секунду, проведённую в коммитах
(сумма событий / сумма `commit_ms` по пачкам окна измерения): сколько
компактор мог бы принять, если бы коммитил без перерыва. «В коммите» — доля
времени компактора в транзакциях (как в этапе 2). «Очередь» — незакоммиченные
события в потоке, опрос раз в 0,25 с, в том числе внутри окна.

## Выводы H3 (только то, что видно в данных)

1. **Ёмкость растёт, занятость падает — эта часть гипотезы подтвердилась.**
   Событий на секунду коммита: на ФС контейнера 4,4–7,4 тыс. при W = 0 →
   11,2–15,0 тыс. при W = 75 (×1,5–2,9); на папке мака 1,1–2,4 тыс. →
   2,0–4,5 тыс. (×1,6–1,9). Доля времени в коммитах при N = 200: 33 → 25 →
   18 % (контейнер), 84 → 71 → 56 % (папка мака); при N = 100 на папке мака
   70 → 57 → 41 %.
2. **Окно спасло единственную точку, где компактор не успевал.** Папка мака,
   N = 200, W = 0: агенты публикуют 2,67 тыс. событий/с, компактор коммитит
   2,04 тыс./с, очередь дорастает до 16,6 тыс. событий, e2e p99 = 6,8 с,
   дозапись 4,5 с. С W = 25 и 75 компактор успевает (2,67 тыс./с), очередь
   ≤ 2,2 тыс., e2e p99 = 1,0 и 0,86 с — но 92–96 % событий доходят до базы
   позже 75 мс. Механизм виден в строках/пачку: их не больше ≈ N при любом
   W, а событий на пачку больше N становится только за счёт схлопывания
   (2,5–3,1 события на строку); стоимость коммита растёт со строками.
3. **Там, где компактор не был узким местом, окно только ухудшило свежесть.**
   На ФС контейнера (занятость при W = 0 ≤ 33 %) e2e p50 выросла с
   0,6–3 мс до 18–30 мс при W = 25 и 55–82 мс при W = 75; p99 — с 11–101 мс
   до 44–88 и 125–180 мс; доля событий дольше 75 мс — ≤ 2 % → ≤ 4 % → 27–66 %.
   Здесь ухудшение предсказуемое: p50 ≈ W, p99 ≈ 1,7–3,5·W.
4. **На папке мака свежесть при N = 50–100 непредсказуема.** e2e p99 при
   N = 50: 126 / 371 / 206 мс (W = 0 / 25 / 75), при N = 100: 487 / 340 /
   709 мс. Крупная пачка — долгий одиночный коммит на этой ФС: p99 коммита
   при N = 100 — 68 → 158 → 211 мс, и он ложится в хвост задержки.
   Часть гипотезы «свежесть ухудшится предсказуемо» на этой ФС не
   подтвердилась.
5. **Схлопывание включается только при W ≥ интервала сброса или при
   очереди.** При W = 25 событий на строку 1,00–1,04 (агент сбрасывает раз в
   75 мс, в окно 25 мс строка попадает один раз), кроме папки мака при

# H1: дельты вместо полной перезаписи (2026-10-04)

**Гипотеза.** Общий файл упирается в объём перезаписи: каждый сброс — UPDATE
полного текста (до 64 КБ). Если писать только приращение, предел одного
файла отодвинется.

(`BEGIN IMMEDIATE`, один коммит на сброс, как у `one-file`). После точки —
`integrity_check` и сверка: склейка чанков последнего сообщения агента =

1. **На ФС контейнера дельты отодвигают предел одного файла.** При N = 200:
   p99 146 мс и 96 % целевых сбросов против 2,7 с и 36 % у полной
   перезаписи; при N = 150 — 109 мс и 98 % против 979 мс и 67 %. Доля
   записей дольше 75 мс — 3,5 % против 14 %.
2. **До N = 100 дельты не хуже лучших прогонов полной перезаписи и сравнимы
   с файлом на сессию:** p99 6 / 12 / 38 мс при N = 20 / 50 / 100 против
   медиан 14 / 46 / 43 мс у `one-file` и 7–36 мс у `file-per-session`.
   При 150–200 файл на сессию всё ещё лучше (65–84 мс против 109–146).
3. **На папке мака дельты порчу не убирают.** 2,9 % записей при N = 5 и 20
   падают с `file is not a database`, `integrity_check` не прошла при N = 20

   агентов — данные теряются или портятся молча. Ошибок порчи меньше, чем у
   полной перезаписи (58–98 % записей), но она есть с N = 5.

   349 и 650 мс, выполнено 89 % и 77 % сбросов (у `file-per-session` —
   598 / 446 мс, 66 % / 47 %).

**Итог по H1:** на «правильной» ФС подтвердилась — объём перезаписи и был
главной ценой общего файла при 150–200 агентах. На папке мака не помогает:
порча не зависит от объёма записи настолько, чтобы исчезнуть.

## Оговорки H1

- Один прогон на точку; разброс `one-file` между прогонами на ФС контейнера
  большой (p99 при N = 50: 14–261 мс), различия до N = 100 — в его пределах.
  При N = 150–200 разница (в 9–18 раз по p99) — больше любого наблюдавшегося
  разброса, но у `one-file` там по одному прогону.
- Чтение не моделируется: собрать текст сообщения из чанков читателю дороже,
  чем прочитать одну строку; размер базы растёт (чанки не сворачиваются).
- p99 `one-file` на папке мака не сравним с append: большинство его записей
  завершились ошибкой порчи быстро.
- Пауз VM нет: ни одной `suspect_pause`, `clock_drift_s` ≤ 0,015 с;
  `gap_max_ms` до 3,7 с на папке мака при N = 100, но одновременных
  стопоров половины агентов нет (`sync_stalls = 0`).

испорченные базы — `~/bench-state/corrupt/one-file-append-*`.

# H2: потоки против процессов (2026-10-04)

**Гипотеза.** Порча общего файла в WAL на папке мака (вывод 1 этапа 1) —
межпроцессная: ломается общая память WAL (`-shm`), которую разные процессы
отображают через bind-mount. Внутри одного процесса SQLite держит одно
отображение `-shm` на все соединения и блокировки между ними — у себя в
памяти, поэтому, если гипотеза верна, потоки порчи не дадут.

**Как мерили.** Режим `one-file-threads`: схема `one-file` (UPDATE полного
текста, WAL), но N агентов — потоки одного процесса, у каждого своё
соединение, созданное в своём потоке. Только папка мака, N ∈ {5, 10, 20},
точка 30 с + 5 с, один прогон, `integrity_check` после точки. Сравнение —
`one-file` (процессы) из `2026-10-04-macos-bind`.

| N | процессы: записей с порчей | процессы: битых баз | потоки: записей | потоки: с порчей | потоки: прочие ошибки | потоки: битых баз | потоки: rate |
|---|---|---|---|---|---|---|---|
| 5 | 668 из 1143 (58 %) | 1 | 1671 | 0 | 0 | 0 | 1,00 |
| 10 | 2015 из 3317 (61 %) | 1 | 3333 | 0 | 0 | 0 | 1,00 |
| 20 | 6268 из 6595 (95 %) | 1 | 6089 | 0 | 0 | 0 | 0,91 |

## Выводы H2 (только то, что видно в данных)

1. **Порчи у потоков нет.** Ноль ошибок порчи и ноль битых баз на 11 093
   записях в трёх точках; у процессов при тех же N — 58–95 % записей с
   порчей и битая база в каждой точке.
2. **Различие не объясняется меньшей нагрузкой** при N = 5 и 10: потоки
   выполнили 100 % целевых сбросов (столько же записей, сколько процессы
   при N = 10, больше, чем при N = 5, где процессы выполнили 69 %).
3. **Это сильный довод за «межпроцессная общая память WAL на этой ФС»**
   и против версий «ломается сам файл базы / WAL-файл на bind-mount»: файлы
   те же, режим журнала тот же, разница — только число процессов,
   отображающих `-shm`.

**Итог по H2:** гипотеза не опровергнута и получила сильное подтверждение;
прямого доказательства (наблюдения рассинхрона `-shm` между процессами) нет.

## Оговорки H2

- **GIL искажает задержки** — p50/p99 потоков (3–4 / 33–254 мс) с процессами
  не сравниваем; смотрим только порчу. При N = 20 выполнено 91 % сбросов
  (разрыв до 1,6 с) — реальная конкуренция за запись там ниже, чем у
  процессов.
- Один прогон на точку, N ≤ 20. Как и на этапе 1, простой тест двух
  процессов (`mmap` + `fcntl`) порчу не воспроизвёл — какое именно свойство
  `-shm` на этой ФС ломается, не установлено.
- Пауз VM нет: `suspect_pause` ни разу, `clock_drift_s` ≤ 0,001 с.
